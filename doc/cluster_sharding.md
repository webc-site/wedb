# 分布式分片与元数据缓存设计方案

## 一、系统定位与核心挑战

在海量多租户场景下，系统需要满足数百万租户的高并发接入、横向水平扩容、高可用故障自动转移以及极致的内存控制。核心挑战与解决目标如下：

1. **写入负载自动打散**：打破单 Leader 写入瓶颈，使不同命名空间的写入流量基于 [`calculate_shard_id`](../cmd/src/sharding.rs#L21-L34) 纳秒级哈希自动分散至集群内不同的物理节点。
2. **百万命名空间支持**：支持数百万乃至上亿租户接入，租户数量增长不增加集群共识与心跳开销。
3. **零数据盲搬迁与最小迁移扩容**：新增节点或故障转移时，优先通过领导权交接（[`transfer_leader`](../cmd/src/sharding.rs#L494-L510)）与增量最小迁移（[`rebalance_incremental`](../cmd/src/sharding.rs#L632-L709)）实现秒级负载均衡，避免全量数据盲目搬迁。
4. **多机架/多可用区容灾**：支持跨机架感知调度（[`register_node_with_rack`](../cmd/src/sharding.rs#L236-L245)），保证分片 3 副本物理隔离于不同机架。
5. **极致内存占用**：多共识组运行开销压缩至单组小于 64 字节；活跃元数据缓存 [`MetaCache`](../cmd/src/meta_cache.rs#L19-L106) 单条小于 20 字节，冷租户零内存开销。
6. **架构职责纯粹解耦**：底层存储引擎彻底剥离认证与会话逻辑，认证逻辑统一上沉至协议接入层。

## 二、分布式多共识组分片架构

为避免单共识组的写吞吐瓶颈，系统采用轻量级虚拟分片池化架构。

### 1. 虚拟分片池化映射

系统不在逻辑上为每个租户单独建立共识组，而是设立固定数量的虚拟分片组（默认 1024 个虚拟分片组）：

$$\text{shard\_id} = \text{rapidhash\_v3}(\text{namespace}) \pmod{1024}$$

无论集群存在 10 个还是 300 万个命名空间，共识组总数恒定为 1024 个。平均每个分片组承载约 3000 个命名空间。

### 2. 节点分散写入与负载均衡

每个分片组由跨物理节点的 3 个副本组成（1 Leader + 2 Followers），各分片组的领导者节点均匀分布在集群的所有物理节点上：

- **分片组 1**：Leader 位于节点 1，承载分配至组 1 的租户写入。
- **分片组 2**：Leader 位于节点 2，承载分配至组 2 的租户写入。
- **分片组 3**：Leader 位于节点 3，承载分配至组 3 的租户写入。

客户端连接集群任意节点时，协议层计算命名空间对应的分片组：
- 若当前节点为该分片组 Leader，直接执行并提交共识日志。
- 若当前节点为 Follower，通过内部高性能通道透明转发至 Leader 节点，或返回重定向指令。

## 三、节点故障转移、动态扩容与机架感知机制

### 1. 节点宕机与秒级故障自愈
当某物理节点异常宕机时，调度器通过 [`auto_heal`](../cmd/src/sharding.rs#L775-L838) 机制自动检测：
- 该节点上担当 Leader 的各个分片组，其位于其他节点的 Follower 副本在 150ms 内心跳超时并快速选举产生新 Leader。
- 从存活且空间充裕（权重 $>0$）的健康机器中挑选副本数最少的节点补齐第 3 副本，数据强一致无丢失。

### 2. 多机架与可用区容灾感知 (Multi-AZ & Rack-Awareness)
通过 [`register_node_with_location`](../cmd/src/sharding.rs#L249-L265) 或 [`register_node_with_rack`](../cmd/src/sharding.rs#L236-L245) 声明节点所属的 **Region（大区）/ Zone（可用区）/ Rack（机架）/ Host（主机）**，SWRR 调度器根据拓扑距离度量公式 $D(u, v)$ 强制将各分片 3 副本打散至不同可用区或物理机架上，天然免疫单机房或单机柜断电故障。

### 3. 增量最小数据迁移扩容 (Minimal Migration)
当集群扩容加入新物理节点时：
- 执行 [`rebalance_incremental`](../cmd/src/sharding.rs#L632-L709)，仅将超载节点上的多余分片副本迁移给新节点（理论最小迁移量 $\approx \frac{3072}{N+1}$）。
- 全集群 90%~99% 的分片副本位置保持物理不动，新节点毫秒级接入并分担写入吞吐。

### 4. 降级待扩容分片自愈 (Under-Replicated Shards Auto-Expansion)
当节点不足（例如单机/双机启动）时，分片处于降级待扩容状态（[`is_degraded`](../cmd/src/sharding.rs#L841-L844)）；随着后续节点通过 `CLUSTER MEET` 上线，调度器执行 [`auto_expand_under_replicated`](../cmd/src/sharding.rs#L874-L929) 毫秒级补齐至满配 3 副本。

## 四、指令原语体系

系统将原语明确划分为集群拓扑原语、元数据管理原语与客户端会话原语：

### 1. 标准 Redis 7.2 集群管理原语 (Standard Cluster Commands)
系统优先采用 Redis 7.2 官方标准集群控制原语，确保标准客户端（`redis-cli -c` / SDK）零修改直接接入：
- `CLUSTER SHARDS`：标准 Redis 7.2 协议，查询集群内所有 1024 个虚拟分片组的 Leader 与副本分布（[`to_cluster_shards_resp`](../cmd/src/sharding.rs#L980-L1034)）。
- `CLUSTER NODES`：查询所有物理节点角色、网络地址与拓扑状态（[`to_cluster_nodes_resp`](../cmd/src/sharding.rs#L1037-L1059)）。
- `CLUSTER INFO`：查询集群健康度、已知节点总数与槽位分配状态（[`to_cluster_info_resp`](../cmd/src/sharding.rs#L1062-L1069)）。
- `CLUSTER MEET <ip> <port> [node_id]`：动态将新节点注册并纳管至集群拓扑，自动触发待扩容分片自愈。
- `CLUSTER SETTAGS <node_id> [region=.. zone=.. rack=.. host=.. weight=..]`：动态配置或修改物理节点的地理机房标签与权重。
- `CLUSTER GETTAGS <node_id>`：查询指定物理节点的四级故障域地理机房标签与权重信息。
- `CLUSTER FORGET <node_id>`：将指定节点从集群中安全剔除并触发副本排空自愈。
- `CLUSTER REBALANCE`：自动触发基于 SWRR 的平滑加权与机架感知全集群分片均衡。
- `CLUSTER FAILOVER`：主动触发分片故障转移与领导权交接。
- `CLUSTER MYID`：查询当前物理节点的 40 位十六进制唯一身份标识。
- `CLUSTER KEYSLOT <key>`：纳秒级计算指定键归属的虚拟分片/槽位编号。
- `CLUSTER COUNTKEYSINSLOT <slot>` / `CLUSTER GETKEYSINSLOT <slot> <count>`：分片槽位键查询。

### 2. 租户与命名空间管理原语 (Namespace Commands)
在标准 Redis 协议之上，仅在多租户管理维度引入简洁的命名空间管理原语：
- `NAMESPACE ADD <名称> <令牌> [分片组编号]`：注册新租户命名空间及鉴权令牌。
- `NAMESPACE SET <名称> <新令牌>`：更新指定租户的访问令牌。
- `NAMESPACE DEL <名称>`：注销租户命名空间并通过底层范围墓碑瞬间释放数据。
- `NAMESPACE GET <名称>`：查询命名空间绑定的令牌信息。

### 3. 客户端会话原语
- `AUTH <令牌>`：基于令牌进行鉴权并绑定连接至对应的租户命名空间。
- `SELECT <数据库编号>`：在当前租户命名空间内切换子数据库。
- `NAMESPACE CURRENT`：查询当前连接所绑定的租户命名空间与数据库信息。

## 五、架构职责分层与彻底解耦

系统遵循单一职责原则对各模块进行清晰划分：

### 1. 存储内核层 (`wedb_embed`)
- **定位**：纯净的本地单机存储引擎，不包含任何网络协议、用户认证、会话状态与密码校验逻辑。
- **核心功能**：基于作用域编号（租户编号与数据库编号）进行保序变长编码、复合数据结构包络定界、前缀范围迭代与范围墓碑删除。

### 2. 协议与会话层 (`webc_cmd`)
- **定位**：网络接入、连接状态管理与 RESP 协议流式编解码。
- **核心功能**：维护客户端连接上下文（认证状态、租户标识、当前数据库编号），负责拦截并校验客户端指令。

### 3. 共识与分片层 (`wedb_raft` / `wedb_cluster`)
- **定位**：分布式共识、虚拟分片路由与元数据广播。
- **核心功能**：维护全局元数据拓扑表（[`ShardTopology`](../cmd/src/sharding.rs#L151-L1070)），驱动数据分片组并行共识，执行请求透明转发与领导权转移。

## 六、极致节约内存的元数据缓存设计

为支持数百万租户并发认证，同时杜绝冷租户常驻内存带来的资源浪费，系统采用定长标量缓存与状态机驱动的强一致同步机制。

### 1. 缓存算法选型
系统选用基于时钟置换（Clock-Pro）算法的轻量级缓存 [`MetaCache`](../cmd/src/meta_cache.rs#L19-L106)：
- 舍弃传统双向链表的指针开销，采用紧凑环形时钟数组与位标记记录访问热度。
- 单条缓存项元数据内存仅约 16 至 24 字节，较传统双向链表方案降低 60% 以上。

### 2. 纯标量定长键值存储
- **键**：令牌字节数组经过 `rapidhash_v3` 计算得到的 64 位无符号整数。
- **值**：包含 64 位租户编号、32 位数据库编号与 32 位版本纪元号的紧凑结构体 [`CachedTenant`](../cmd/src/meta_cache.rs#L11-L16)。
- **内存开销**：单条记录完全内联于紧凑数组中，单条物理内存仅约 16 至 20 字节。
- **容量收益**：缓存 10 万个热点活跃租户仅需约 1.8 MB 内存，数百万个冷租户在未连线时不占用任何内存。

### 3. 多节点缓存强一致同步机制
当管理员在集群中执行令牌更新或租户注销时，系统通过共识状态机提交钩子实现全集群本地缓存的天然强一致同步：
1. 所有元数据变更指令统一作为共识日志提交至系统元数据管道。
2. 全集群各节点的共识状态机在应用日志并写入本地底层存储时，统一触发元数据变更钩子。
3. 状态机在写入存储的同时，直接调用本地缓存的失效方法清除旧令牌哈希。
4. 全程完全复用现有的共识日志管道，无需额外的网络广播或反向代理通知，且日志应用顺序在全集群严格全序，从根本上杜绝时序混乱与脏缓存残留。
