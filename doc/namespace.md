# 命名空间与多数据库架构设计

## 一、系统定位与设计目标

在分布式与嵌入式多租户存储场景中，系统需要同时支持百万级租户以及单租户下无上限的数据库选择。系统设计目标如下：

1. **百万租户支持**：租户标识采用 64 位无符号整数，容量达到 1844 亿亿（$2^{64}-1$），彻底解除传统系统对租户数量的限制。
2. **无上限数据库**：每个租户内部支持独立的 64 位无符号整数数据库编号，支持任意切换与动态分配，无需预先创建模式。
3. **紧凑编码与保序存储**：编码后的前缀必须严格保持原数值的字节字典序，以兼容底层 LSM-Tree 存储引擎的范围前缀扫描。
4. **物理隔离与零冲突**：支持任意二进制键，杜绝用户键与租户、数据库及内部数据结构子键的前缀混淆。

## 二、保序前缀变长整数编码 (OPPV)

为兼顾小数值的高压缩比与大数值的超大容量，并严格保证编码后字节序列的字典顺序与原数值大小完全一致，系统采用保序前缀变长整数编码算法（[`encode_u64_varint`](../embed/src/scope.rs#L19-L75) / [`decode_u64_varint`](../embed/src/scope.rs#L79-L103)）。

### 1. 编码原理

编码使用一元前缀头（Unary Prefix Header）表示长度。首字节高位连续二进制 1 的个数加 1 即为整个编码占用的字节总数。解码时可通过硬件指令单周期完成长度识别，无需依赖任何分隔符。

### 2. 字节分布与容量规划

| 取值范围 | 占用字节数 | 前缀位特征 | 适用场景 |
| :--- | :--- | :--- | :--- |
| $0 \sim 127$ | 1 字节 | `0xxxxxxx` | 默认租户、常用系统数据库 |
| $128 \sim 16511$ | 2 字节 | `10xxxxxx` | 早期及中小型租户集群 |
| $16512 \sim 2113663$ | 3 字节 | `110xxxxx` | 百万级租户主力区间 |
| $2113664 \sim 270549119$ | 4 字节 | `1110xxxx` | 亿级超大规模租户 |
| $270549120 \sim 2^{64}-1$ | 5 至 9 字节 | `1111xxxx` | 极端超大数值范围 |

### 3. 保序性与前缀扫描

对于任意两个 64 位无符号整数 $A$ 和 $B$，若 $A < B$，则编码后的字节数组在逐字节比较时必定满足：
$$\text{encode}(A) < \text{encode}(B)$$
这使得底层存储引擎能够直接利用字节前缀进行范围迭代，高效执行单库清理与租户级数据遍历。

## 三、物理键存储结构与作用域定义

作用域 [`ScopeId`](../embed/src/scope.rs#L109-L301) 由租户编号（`tenant_id: u64`）与数据库编号（`db_id: u64`）组合而成。

### 1. 物理键结构

对于非默认作用域，所有数据键、元数据键与子项键均统一采用双零引导符开头，结构如下：

$$\text{Key} = \texttt{0x00}\texttt{0x00} + \text{Varint}(\text{tenant\_id}) + \text{Varint}(\text{db\_id}) + \text{TypeTag} + \text{UserKey}$$

类型标签约定如下：
- 字符 `k`：通用字符串键值
- 大写字母（如 `H`, `L`, `Z`, `S`）：哈希、列表、有序集合、集合等复合数据结构的元数据键
- 小写字母（如 `h`, `l`, `z`, `s`）：复合数据结构的内部数据子键

### 2. 复合结构内部子键的定界包络

为防止复合结构中的主键与字段内容发生穿透，数据子键采用长度前缀包络：

$$\text{SubKey} = \text{ScopePrefix} + \text{TypeTag} + \text{BigEndian32}(\text{KeyLen}) + \text{KeyBytes} + \text{BigEndian64}(\text{Version}) + \text{FieldBytes}$$

主键长度明确界定了主键边界，版本号隔离了不同生命周期的残留数据。

## 四、客户端交互与执行流程

### 1. 鉴权与租户绑定
客户端连接后通过 `AUTH` 命令提交令牌。系统在专用的鉴权物理命名空间中查询令牌对应的租户编号，并将当前连接上下文绑定至该租户，默认数据库编号为 0。若为管理员身份，则绑定至根租户 0。

### 2. 数据库动态切换
客户端发送 `SELECT <db_id>` 命令切换数据库编号时，系统仅在内存连接上下文中更新数据库编号字段。无需执行任何磁盘元数据初始化或模式创建，下次读写请求自动携带新的数据库前缀。

### 3. 运维清理机制
- **单库清理**：构造当前租户与当前数据库的前缀（[`flush_db_prefix`](../embed/src/scope.rs#L214-L220)），通过底层迭代器批量扫描并清理关联的数据键与元数据键。
- **租户清理**：构造当前租户的前缀（[`tenant_prefix`](../embed/src/scope.rs#L223-L229)），遍历并删除该租户下所有数据库的全部数据与元数据。

## 五、二进制键冲突防御体系

1. **自定界变长前缀**：变长整数首字节严格决定字段长度，无需文本分隔符，彻底杜绝特殊字符截断与注入。
2. **长度前缀定位**：复合结构子键显式记录主键字节长度，支持包含空字节在内的任意二进制主键。
3. **版本号围栏**：每次删除并重建同名复合键时分配递增版本号，历史残留子键在新版本下自动失效。
4. **物理命名空间隔离**：底层将用户数据、元数据与鉴权映射分别存放于三个独立的物理存储区域，用户层面的读写无法接触或伪造系统级鉴权信息。
