问题分析：
1 Garnet 契约对齐：C# WaitForCommit 档（EnableAOF 且 aof-commit-wait）的对客承诺是「应答出网前阻塞等待 AOF 提交落盘」。复位判据 HandleAofCommitMode（garnet/libs/server/Resp/Parser/RespCommand.cs:1267-1283）为 dcurr == networkSender.GetResponseObjectHead()，即响应缓冲内有未出网字节时绝不复位；应答字节唯一致命出口 Send（garnet/libs/server/Resp/RespServerSession.cs:1451-1463）先 WaitForCommitAsync 后发。脚本内 redis.call 重入的是内嵌独立 processor（garnet/libs/server/Lua/SessionScriptCache.cs:24-26/:60-64，new RespServerSession + ScratchBufferNetworkSender），外层会话的 dcurr 与 waitForAofBlocking 在整个脚本期完全不被触及：外层判据恒见前序应答在场不复位，外层 Send 照常等待。C# 结构上不存在脚本窗破坏外层 commit-wait 的路径。
2 工程现状确证：rust 无内嵌 processor，脚本窗口以换出会话缓冲等价承接（wedb/wnode/src/resp/resp_server_session/lua.rs:252 let outer_output = mem::take(&mut self.output)，resume_suspended_script 同款 :123）。窗口快照/还原面只覆盖游标、resp_protocol_version、active_db_id、output_watermark_yield（lua.rs:257-261 入口、:301-311 收尾），不含 wait_for_aof_blocking。窗内每条 redis.call 经 session.try_consume_messages() 重入共享会话解析（lua.rs:501-502），解析门控无条件调 handle_aof_commit_mode（wedb/wnode/src/resp/parser/resp_command.rs:274-276），其复位臂读 pending_output_len()==0（resp_command.rs:480-482，pump.rs:180-182 即 self.output.len()）——读到的是换出后的空壳缓冲，标记被复位；若该 redis.call 属 AOF 独立集（resp_command.rs:71-127，PING/TIME/INFO/CONFIG GET/CLIENT 族等）则复位后保持 false。窗口关闭只还原缓冲不还原标记（lua.rs:309 self.output = outer_output、:314 追加 script_out），出网臂 drive.rs:371 读 false 跳过 wait_for_commit_async，前序 AOF 相关命令应答未经 fsync 直发。同机制次生面：with_bypass_buffer（resp_command.rs:438-448）驱动的 redis.acl_check_cmd（lua.rs:578-581 唯一生产消费位）窗内解析同样落外层标记。触发形态精确化：--aof-commit-wait 连接，同批「前序 AOF 相关命令（如 SET）+ 尾部 EVAL，且脚本窗内最后解析的 redis.call 属 AOF 独立集」；批尾若再解析 AOF 相关命令会重新置位自愈，纯写脚本亦自愈（写命令非独立集，复位后随即置回 true）。
